Ansible cheat sheet

Quick reference — see Lesson 2 for the full explanation.

What it is

Configuration management: brings an already-existing machine (or API-managed resource) to a desired state. Contrast with Terraform, which provisions the resource's existence in the first place. In practice the line blurs (Ansible has cloud modules too), but this is the default split.

Idempotency

Running the same playbook twice should converge to the same end state as running it once. A task reports changed if it had to act, or ok if the system already matched. This is what makes re-running a playbook safe.

Idempotency is a promise about Ansible's own view converging — it says nothing about a second tool (Terraform) independently re-asserting a different value for the same field. See Lesson 2 for the full drift bug this caused in session-08.

Core vocabulary

  • Inventory — the list of hosts/targets a playbook runs against.
  • Playbook — an ordered list of tasks (YAML) to apply.
  • Role — a reusable, packaged bundle of tasks/files/templates.
  • Ansible Vault — encrypts sensitive variables/files at rest; the Ansible-native answer to "don't commit a plaintext secret" (ansible-vault create|edit|view secret.yml).

Push vs. pull

Ansible is push-based: a control node connects out (typically over SSH) and runs tasks. Contrast with Argo CD, which is pull-based: a controller inside the cluster continuously pulls toward the desired state. Naming this contrast out loud is good trade-off-reasoning material in a design interview.

The "two writers" smell

Before proposing Ansible (or any tool) to own a value, ask: does anything else in this design also write to the same field? If yes, that's the shape of the session-08 bug — not an Ansible-specific flaw, but a general architectural smell worth naming proactively.

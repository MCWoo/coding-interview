Observability cheat sheet

Quick reference — see Lesson 3 for the full explanation.

Three signals

Metrics Numbers over time. Cheap, basis for alerting/dashboards.
Logs Discrete timestamped events with full detail.
Traces A request's path across services, as spans.

Monitoring says a problem exists. Observability is having enough signal to figure out why, for a question you didn't predict in advance.

Why native tools alone don't solve cross-cloud visibility

CloudWatch (AWS) and Azure Monitor (Azure) are both fine within their own cloud — neither knows the other exists. "Use the native tool" quietly answers "what's running in this one cloud," not the actual requirement.

Two real approaches

  1. Federation/aggregation layer — a vendor-neutral collector (e.g. an OpenTelemetry Collector) runs in both clouds and ships all three signals to one shared backend.
  2. Consistent resource tagging — every resource in both clouds needs the same tags (owner, environment, cost-center) or no query layer can answer "what's running and whose is it," regardless of pipeline sophistication. Enforce this at the same layer as security guardrails (e.g. a Terraform module that requires tags to provision).

Official docs: OpenTelemetry: Concepts — Signals · Prometheus: Overview

No official source directly documents "cross-cloud visibility" as its own named problem (see RESOURCES.md → Gaps) — the two-approaches framing above is a synthesis, reasonable but worth treating as your own reasoning in an interview, not a quoted best practice.

Ansible idempotency and the Terraform drift bug

Lesson 2 of 3 — this one rebuilds the exact bug from session-08: a default password rotated quickly by Ansible, reset right back by the next terraform apply.

In the interview, the proposal was: ship a default password, then have Ansible rotate it fast. The bug wasn't caught until a follow-up question forced it out — the goal here is to make that bug obvious before proposing the design, not after.

What idempotency actually promises

Ansible's core design idea: running the same playbook twice should produce the same end state as running it once. A task either reports "changed" (it did something) or "ok" (the system already matched the desired state, so it did nothing). This is what lets you re-run a playbook safely instead of tracking by hand whether it's already been applied.

That promise is about Ansible's own view of the system converging. It says nothing about what happens when a second tool — Terraform, in this case — has its own independent idea of what the correct state is, and periodically re-asserts it.

Fill in the blank: when an Ansible task actually does something because the system didn't already match the desired state, it reports ____.

Reconstructing the bug

Walk the sequence from session-08 step by step:

  1. Terraform provisions a resource with a default password baked into its config (or a variable it set).
  2. Ansible runs afterward and rotates that password to something new — as far as Ansible is concerned, this converges the system to the "rotated" desired state, and it reports success.
  3. Later, anyone (a teammate, a CI job, a scheduled drift-detection run) runs terraform apply again.
  4. Terraform compares the live resource against its own state file — which still says "default password" — sees a difference, and "fixes" it by writing the default password back.

Nothing in step 4 is a bug in Terraform. Terraform is doing exactly what it's designed to do: reconcile reality against its recorded state. The bug is architectural — two systems each believe they alone own the same piece of data, and neither one knows about the other's writes.

The generalizable lesson, not just this one bug: any time a design has two different tools capable of writing to the same field/value, ask "what happens when both decide to act on it independently?" before asking whether either tool individually works. This is the trade-off-framing move from the interview feedback — naming the tension before being asked about it.

What actually breaks the tie

The fix the candidate eventually reached in the interview (correctly, once reached): let the cloud-managed service itself own credential generation — e.g. a managed database's own integration with a secrets manager generates and stores the credential directly. Terraform's job shrinks to granting IAM access to that secret, not generating or holding the value. This removes the second writer entirely, rather than trying to choreograph two writers more carefully.

Primary sources — read before the next session: Ansible: Introduction to Playbooks (official docs, for idempotency/changed-state mechanics) and Ansible Vault (official docs, for how Ansible's own answer to "don't commit a plaintext secret" compares to the Terraform-state-plaintext problem from the same session).

GitOps and what Argo CD actually owns

Lesson 1 of 3 on the gaps from session-08 — this one targets the exact spot where the interview went sideways: treating Argo CD as something that deploys infrastructure.

In the mock interview, the first instinct was "use Argo CD to deploy infrastructure." That got corrected mid-conversation, but it's worth rebuilding the idea from its foundation so the correction sticks on its own, without needing a nudge next time.

The inversion GitOps makes

A traditional CI/CD pipeline pushes: a job builds an artifact, then runs kubectl apply or similar from outside the cluster, reaching in to change it. GitOps flips this. A controller that already lives inside the cluster continuously compares the live state of the cluster against a Git repository, and pulls whatever changes are needed to make the two match. The pipeline's job shrinks to "update the repo" — the controller does the actual reaching-in.

Argo CD is that controller. Its job, stated precisely: watch one or more Git repos containing Kubernetes manifests (or Helm charts, Kustomize overlays, etc.), and keep a target cluster/namespace in sync with what's declared there.

This is the whole scope. Argo CD's unit of work is a Kubernetes manifest. It has no model of a cloud VM, a VPC, an IAM role, or a managed database — those don't exist in the Kubernetes API that Argo CD is watching. Anything upstream of "a cluster already exists and I have manifests to apply to it" is not Argo CD's job, full stop.

Three mechanics worth having cold

These three terms come up constantly once "Argo CD manages manifests" is established, because they're how it decides what to do when it notices a difference:

  • Sync — the act of reconciling: when the live cluster state doesn't match the Git-declared state (an "OutOfSync" Application), sync applies whatever's needed to converge them. Can be triggered manually or automatically.
  • Self-heal — off by default. If someone runs kubectl edit directly against a live resource, self-heal makes Argo CD notice the drift and revert it back to what Git says, rather than leaving the manual change in place.
  • Prune — also off by default, for safety. If a resource is deleted from the Git repo, pruning tells Argo CD to delete the corresponding live resource too, instead of just ignoring it.

Primary source — read this before the next session: Argo CD: Core Concepts (official docs). For the sync/prune/self-heal mechanics specifically: Automated Sync Policy.

Applying this back to the interview

The platform you designed in session-08 needed Argo CD to do exactly one job: once a cluster exists and the manifests are in a repo, keep workloads in sync with that repo. Everything before that point — provisioning the cluster itself, the VPC it sits in, the IAM roles it assumes — is Terraform territory, not Argo CD's. A clean way to say this out loud in an interview, unprompted: "Argo CD picks up once there's a cluster and manifests to reconcile — everything before that is still Terraform's job." That one sentence would have pre-empted the nudge you got last time.

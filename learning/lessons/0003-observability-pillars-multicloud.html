Observability across two clouds

Lesson 3 of 3 — this is the requirement that never got addressed at all in session-08: "know what's actually running across both clouds without manually auditing each team's footprint."

Unlike the Argo CD and Ansible gaps, this one wasn't a wrong answer — it was a blank. The goal here is just to have a baseline vocabulary and a first-pass design so the next session has something to say instead of silence.

The three signals, vendor-neutral

Before anything cloud-specific, there's a standard split (formalized by OpenTelemetry, now the common cross-vendor vocabulary for this) into three signal types:

  • Metrics — numbers measured over time (request count, latency, CPU). Cheap to collect and store, and the usual basis for alerting and dashboards.
  • Logs — discrete, timestamped records of specific events, carrying detail metrics can't (a stack trace, a failed query, the exact input that triggered an error).
  • Traces — the path of a single request as it crosses multiple services, each hop recorded as a "span," so you can see where time was actually spent across a distributed call.
A useful one-line distinction: monitoring tells you a problem exists (a metric crossed a threshold); observability is having enough signal — usually a mix of all three — to figure out why, without having predicted the specific question in advance.

Why "just use CloudWatch" doesn't solve the actual requirement

AWS ships CloudWatch; Azure ships Azure Monitor. Both are perfectly good at observing resources within their own cloud. Neither one knows anything about the other. If the platform's requirement is "what's running across AWS and Azure," a design that just says "use each cloud's native tool" has quietly answered a different, easier question.

Two real approaches to the actual cross-cloud problem, roughly in order of how often they come up in practice:

  1. A federation/aggregation layer — a vendor-neutral collector (an OpenTelemetry Collector is the common default) runs alongside workloads in both clouds and ships all three signal types to one shared backend, so there's a single pane of glass regardless of which cloud emitted the data.
  2. A consistent resource-tagging scheme — this is the less glamorous half, and the one that's easy to skip in an interview answer: raw metrics/logs are useless for "what's running and whose is it" unless every resource in both clouds carries the same tags (owner, environment, cost-center) that a query layer can group by. No amount of pipeline sophistication fixes an untagged resource.
Tagging consistency is infrastructure, not an observability tool — it's usually enforced at the same layer as the "security guardrails by default" requirement from the same problem (e.g. a Terraform module that refuses to provision a resource without the required tags). Worth connecting those two requirements explicitly in a design answer rather than treating them as unrelated asks.
